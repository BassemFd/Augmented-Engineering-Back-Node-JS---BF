# Documentation Guidelines

These guidelines apply to all documentation in the Bel'Air's Buvette project (code, API, architecture, user guides, etc.). Their purpose is to ensure clarity, consistency, and maintainability of documentation, to facilitate onboarding, collaboration, and knowledge transfer.

## Objectives

- Make the project understandable and accessible to everyone (newcomers, contributors, users).
- Document technical choices, architecture, APIs, workflows, and important decisions.
- Keep documentation up to date and aligned with the codebase and practices.
- Foster collaboration and contribution through shared standards.

---

## Writing Best Practices

- Prioritize clarity, conciseness, and pedagogy: write to be understood by a newcomer.
- Structure documentation with explicit titles, short sections, and bullet lists.
- Use Markdown for all documents (README, guides, specs, etc.).
- Add concrete examples, diagrams, or code snippets to illustrate concepts.
- Explain the "why" behind technical choices, not just the "how".
- Write in English (or French if the repository convention requires), but stay consistent within each document.
- Update documentation as soon as a code or process change makes it obsolete.
- Specify the last update date and author if relevant.

## Types of Documentation to Maintain

- **README.md**: Presents the project, its objectives, installation, usage, and useful links.
- **Contribution guides**: Explains how to contribute (conventions, git workflow, code review, etc.).
- **Architecture documentation**: Describes the overall architecture, key decisions, major dependencies, diagrams.
- **Functional and technical specifications**: Details requirements, use cases, APIs, data models.
- **Code documentation**: Comments on complex parts, exposes public interfaces, documents key modules.
- **Changelogs**: Lists changes, fixes, and breaking changes for each version.
- **FAQ and user guides**: Answers frequent questions, explains major workflows or features.

## Documentation Checklist

- [ ] The document has a clear title and introduction
- [ ] Sections are structured and hierarchical
- [ ] Examples, diagrams, or code snippets are present if relevant
- [ ] Technical choices and their justification are explained
- [ ] Documentation is up to date with the codebase and practices
- [ ] Links to other resources or documents are present if needed
- [ ] Last update date is indicated if relevant
- [ ] The style is consistent, inclusive, and accessible

## Best Practices and Advice

- Review and have documentation reviewed by other team members.
- Take user feedback and questions into account to improve docs.
- Don't hesitate to refactor or move documentation to avoid redundancy.
- Use automation tools (API doc generation, link checking, etc.) if possible.
- Also document limitations, points of attention, and pitfalls to avoid.
- Remember that documentation is living: update it regularly, even for small changes.
